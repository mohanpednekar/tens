## 2024-06-25 - Prevent O(N) performance drops with O(1) math batching in tickGame autobuyers
**Learning:** In `tickGame`, when processing massive offline progress (large `budget`), the `while (budget >= 1)` loop iteratively evaluated and purchased units for a single attempt (e.g. 10 units) at a time. Each attempt created a new clone of the massive immutable state object by calling `buyTierQuantity`. If a player afforded 1,000 attempts within the same level boundary, this caused 1,000 redundant deep clones resulting in severe performance drops and thread freezes.
**Action:** Replaced the `O(N)` loop (where `N` = number of affordable attempts) with an `O(1)` mathematical batching calculation bounded by the current level. The loop now calculates exactly how many affordable attempts fit within the remainder of the current level and executes them all in a single `buyTierQuantity` step. The loop gracefully resumes on the next level boundary if any `budget` is left, changing time complexity from `O(budget)` to `O(levels crossed)` which is functionally O(1) for large idle accumulations since costs increase exponentially.

## 2024-09-20 - Replace O(N) Compute Flops autobuyer with O(1) mathematical formulation
**Learning:** In idle/incremental games, autobuyers accumulating large attempt budgets trigger O(N) `while` loops (like `tickComputeFlopsAutobuyers`), freezing the main thread and recalculating costs on each single-unit purchase. Calculating the total maximum affordable quantity iteratively is inefficient for exponential cost functions.
**Action:** Use an O(1) equivalent by factoring max attempts directly into a `getComputeFlopsAffordableAndCost` and `buyComputeFlopsTierQuantity` mechanism which reduces total processing overhead. Wait, calculating exponential growth costs directly inside a loop that's bounded strictly by max attempts is okay for this specific `budget` constraint because the scale and attempts limit its N to small values, but the key performance win is avoiding deep-cloning the immutable state tree in `buyComputeFlopsTier` N times. Replacing N object spreads with a single bulk update saves massive memory allocations and garbage collection overhead.

## 2024-10-24 - Replace O(N) iterative loop in tickDiskAutoFill with O(1) mathematical formulation
**Learning:** During massive offline progress intervals, simulating `tickGame` thousands of times exposes an O(N) `for (;;)` iterative chunking loop in `tickDiskAutoFill`. This loop repeatedly transfers `blockBits` blocks of cache data from `poolBuffers` to `diskCache` until depleted or budgeted. This iteratively subtracting calculation can freeze the main thread, operating as a severe performance bottleneck for large accumulated capacities.
**Action:** Replaced the iterative `for (;;)` subtraction loop with an O(1) bulk chunk mathematical formula using `Math.floor(available / blockBits) * blockBits` which executes natively, immediately evaluating the total exact `transferUnit` without repeatedly jumping through branch evaluations. The new single-pass math fully mirrors the logic, preventing the offline progress thread freeze while maintaining block-size precision logic.

## 2024-10-25 - Replace O(N) iterative loop in getDataLakeManualFillBitsNeeded with O(1) mathematical formulation

This loop iteratively evaluates sub-sizes and subtracts `fillBits`, creating a performance bottleneck when `neededUnits` is massive.

## 2024-11-06 - Replace O(N) object spreading in tick loops with direct mutation
**Learning:** Performing `O(N)` object spreading inside hot game loop components like `tickDiskAutoFill` creates an enormous number of intermediate garbage objects (e.g. `{...diskCache, [size]: ...}` for every tier pool) that stress the garbage collector and cause main thread pauses.
**Action:** Always replace deep or shallow spreading inside `for` loops by cloning the object once upfront (`const diskCache = { ...state.diskCache }`) and locally mutating that clone (`diskCache[size] = ...`, `delete diskCache[size]`) before finally passing the mutated clone down into the returned immutable state tree. This converts `O(N)` allocations into `O(1)` upfront cost.

## 2024-10-28 - O(N) Loop Replacement Dimensionality Check
**Learning:** When attempting to replace iterative `while` loops processing massive scale incremental progression with O(1) mathematical chunks (e.g. data lake bits to disk unit conversions), it is critical to keep the dimensions (units vs. slots vs. capacities) aligned to avoid state corruption. Incorrectly intermingling variable capacities meant to represent slots with those meant to represent base units causes disastrous overflow bugs that aren't immediately caught without precise state boundary checks.
**Action:** Always strictly verify dimensionality in formulas (like deriving `maxAvailable` bounds and `slotsToBuy`) and ensure any `if/else` breakout conditions in the O(1) loop perfectly replicate the boundary constraints of the original logic.

## 2024-11-20 - Prevent massive GC overhead by hoisting dynamic object allocations out of hot loops
**Learning:** In `src/game/engine.js`, the `tickDiskAutoFill` function iterated through `flushSizes` in its Pass 3 phase. Inside this tight `for` loop, it continually evaluated `isDiskRedeemable` by passing an inline deeply-spread object (`{ ...state, intro: { ...state.intro, poolBuffers, disks, diskCache, diskReadCacheFlush } }`). Generating this heavy nested object entirely anew on every single iteration caused extreme memory allocations and garbage collection thrashing during large batch processes (like calculating massive offline progress). Furthermore, providing a fresh object reference continuously breaks any potential underlying Redux/memoization caches.
**Action:** Always inspect loops in hot simulation paths (like `tickGame` and related sub-ticks). If a derived state is needed for a read-only query (like `isDiskRedeemable`), hoist the snapshot creation *outside* the loop (`const checkState = { ...state, intro: { ... } }`). Since locally mutated properties (like `diskCache`) are mutated by reference within the same scope, the hoisted `checkState` object will naturally reflect these mutations inside the loop without needing reallocation, turning an `O(N)` GC spike into an `O(1)` cost.

## 2024-11-20 - Prevent massive GC overhead by hoisting dynamic object allocations out of hot loops in tickDiskWriteCache and tickDiskAutoFill
**Learning:** In `src/game/engine.js`, the `tickDiskAutoFill` and `tickDiskWriteCache` functions process multiple loops iteratively where they check a dynamically generated immutable snapshot via object spread syntax. In large iterations where these operations are simulated repeatedly for offline progress catching-up, repeatedly cloning the object via `...state` allocations causes intense GC thrashing. Using `Object.defineProperties` allows lazy getters to point to the local reference variables, turning `O(N)` GC allocation into `O(1)` zero-allocation references.
**Action:** When an immutable reference to the outer state is required for a read-only query within a tight loop mutating local variables (e.g. `isDiskRedeemable(snapshot())`), initialize the object once before the loop and use `Object.defineProperties` with getters that close over the `let` local variables, skipping repeated spread allocations entirely.
